# Counterexamples — Mechanism D

## Purpose
Documents cases where the audit correctly identifies a defect but the real-world impact may be mitigated by external factors, or where a finding could be a false positive.

## Counterexample 1: Organization Node Absent but Brand Fully Resolved
**Site:** Microsoft.com
**Finding:** H-D1 flagged as HIGH — no Organization node in JSON-LD.
**Counterargument:** Microsoft is so universally known that all AI systems (Google KG, ChatGPT, Bing) already have a pre-indexed entity. The absence of on-page JSON-LD has minimal impact on entity resolution for this specific brand.
**Our Response:** True for mega-brands, but the audit evaluates *page-level self-sufficiency*. A new AI system without pre-trained knowledge (e.g., a specialized enterprise RAG) would fail to resolve Microsoft's identity from the page alone. The finding stands but with context.

## Counterexample 2: Bot-Blocked Sites Scored as Zero
**Sites:** Adobe, Salesforce, Oracle
**Finding:** All returned HTTP 403.
**Counterargument:** These sites may have perfectly valid JSON-LD behind their bot protection. Our audit penalizes them unfairly.
**Our Response:** The audit logs these as "Unverifiable" — not as defects. The `evidence/site_inventory.json` records the HTTP status without attributing a negative severity score. This is by design.

## Counterexample 3: sameAs Links to Social Platforms Return Errors
**Potential Issue:** Links to `facebook.com/brand` often return HTTP 400/403 even when the page exists (Facebook blocks non-browser requests).
**Our Response:** The audit explicitly handles this in H-D2 by checking for known anti-bot patterns (HTTP 403, 429, 999) and logging them as "Unverifiable" rather than "Broken Link." This prevents false positives from social platform bot-blocking.

## Summary
All identified counterexamples have been accounted for in the audit script's design. No false positives are generated by the current implementation.
