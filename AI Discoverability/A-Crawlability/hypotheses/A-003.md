# A-003 — Important URL Retrieval Failure

## Mechanism
crawl

## Concrete Claim

IF:
a meaningful portion of important public URLs on a site repeatedly fail to return usable HTTP responses (persistent 4xx errors, 5xx server errors, connection timeouts, DNS failures, or unresolvable redirect chains),

THEN:
a crawler cannot reliably retrieve the content at those URLs, and the affected pages cannot proceed to the read/extract stages of the machine pipeline.

## Evidence Needed

### To Confirm
- Sample a set of important public URLs (from sitemap, navigation, or internal links)
- Make bounded HTTP requests to each URL with appropriate timeouts
- Record: status code, final URL after redirects, redirect chain length, response time, content type
- Repeat requests to distinguish persistent from transient failures (minimum 2 attempts with delay)
- Calculate the proportion of important URLs that persistently fail
- Verify that failing URLs are genuinely important (not intentionally removed or redirected to equivalent content)

### To Reject or Narrow
- Failures are transient (succeed on retry) → NOT a persistent retrieval failure
- Failed URLs have been intentionally removed and properly return 410 Gone → expected behavior
- Failed URLs redirect to valid equivalent content (e.g., 301 to canonical URL) → NOT a failure
- The site is undergoing temporary maintenance → transient, not architectural
- Failed URLs are low-importance (supplementary pages, old blog posts) → reduced severity

## Observable Signal
Multiple important public URLs return non-2xx status codes, time out, or fail to resolve on repeated attempts.

## Automated Decision Boundary
A finding is generated when:
1. A sample of ≥20 important public URLs is tested, AND
2. ≥10% of sampled important URLs persistently fail (non-2xx on ≥2 attempts with ≥5s delay between), AND
3. The failures are not exclusively 301/302 redirects to valid destinations, AND
4. The failing URLs are classified as important (from navigation, sitemap with high priority, or major content sections)

Severity scales with the proportion and importance of affected URLs.

## Potential Severity

**Critical**: >50% of sampled important URLs persistently fail to return usable content.

**High**: 25-50% of sampled important URLs persistently fail.

**Medium**: 10-25% of sampled important URLs persistently fail.

**Low**: <10% but >0 important URLs persistently fail, or failures are limited to supplementary content.

## Potential Remediation
Investigate and resolve the root cause of persistent HTTP failures for important public URLs. Common fixes include: repairing broken internal links, resolving redirect chains to valid destinations, fixing server configuration errors causing 5xx responses, removing or properly redirecting URLs for content that has been moved, and ensuring DNS records are correctly configured for all serving domains.

## Current Evidence

**SOURCE-DERIVED FACT**: HTTP semantics (RFC 9110) define status codes 4xx as client errors and 5xx as server errors. A 404 indicates the resource was not found; a 500 indicates a server failure. Neither returns usable page content.

**SOURCE-DERIVED FACT**: Google Search Central documents that persistent 404/5xx errors cause Googlebot to reduce crawl rate and eventually drop URLs from the index.

**OUR INFERENCE**: If a crawler encounters persistent retrieval failures on important URLs, the content at those URLs is mechanistically unavailable for downstream processing.

**UNPROVEN DOWNSTREAM EFFECT**: Direct impact on AI assistant citations from retrieval failures is not established by this research.

## Counterexamples

1. **One transient 500** → NOT a finding. A single server error that resolves on retry is transient, not architectural.

2. **Valid permanent redirect (301)** → NOT a finding. A 301 redirect to a working canonical URL is proper URL management, not a retrieval failure.

3. **Intentionally removed content (410 Gone)** → NOT a finding. The 410 status code explicitly communicates intentional removal.

4. **Low-importance pages returning 404** → NOT a high-severity finding. Old blog posts or supplementary pages that no longer exist may not warrant attention.

5. **Rate-limited responses (429)** → NOT a site defect finding. This indicates the audit tool is making too many requests; the script should respect rate limits.

## Known Limitations
- Cannot distinguish between intentionally removed content and broken links without context
- Transient failures require multiple requests to classify, adding time
- Rate limiting by the target server may cause false retrieval failures
- Cannot test URLs behind authentication (by design — read-only, no login)
- Sample size is bounded; large sites may have failures in untested sections
- Does not account for CDN-level failures that may be region-specific

## Experiment Design

1. **Condition tested**: Important URLs persistently returning non-2xx responses
2. **Expected bad outcome**: Crawler cannot retrieve content at those URLs
3. **Ground truth**: HTTP status codes from actual requests
4. **Supports hypothesis**: ≥10% of important URLs fail persistently
5. **Kills hypothesis**: All important URLs return 2xx or valid redirects
6. **Obvious false positives**: Transient errors, valid redirects, intentional removals
7. **Automatable**: Yes — fully deterministic
8. **Works on unseen site**: Yes — HTTP is universal
9. **Evidence emitted**: URL-by-URL status codes, failure rates, redirect chains
