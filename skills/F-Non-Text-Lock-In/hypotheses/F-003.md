# F-003 — Non-Text Interactive/Visual Fact Lock-In

## Mechanism
lock-in

## Concrete Claim

IF:
important factual information (data values, instructions, specifications, or key content) is communicated only through a non-text interactive or visual presentation layer — such as `<canvas>` elements, `<video>` without transcript/captions, CSS-generated content, SVG with embedded text, or interactive data visualizations — and there is no equivalent readable textual representation in the page's HTML,

THEN:
a text-oriented machine reader will be unable to reliably retrieve or quote that information, because the content exists in a format that text extraction cannot parse.

## Evidence Needed

### To Confirm
- Detect `<canvas>`, `<video>`, `<object>`, `<embed>`, and large SVG elements on the page
- For `<video>`: check for `<track>` elements (captions/subtitles), nearby transcript text, or ARIA descriptions
- For `<canvas>`: check for fallback content within the `<canvas>` tags, `aria-label`, or nearby text equivalents
- For SVGs: check whether text content is encoded as actual `<text>` elements (extractable) or as paths/images (not extractable)
- Identify CSS-generated content (`content:` property) that may contain factual text
- Verify that the non-text element appears in a factual content area and likely contains important information
- Demonstrate that text extraction of the page misses the facts communicated by the non-text element

### To Reject or Narrow
- The video has a `<track kind="captions">` or `<track kind="subtitles">` → text equivalent exists
- A full transcript is provided in the page HTML → text equivalent exists
- The canvas element has descriptive ARIA attributes or fallback content → accessible representation exists
- The SVG contains `<text>` elements that are extractable → text content is accessible
- The non-text element is purely decorative (background animation, loading spinner) → not factual content
- Equivalent facts appear in nearby HTML text → text representation exists

## Observable Signal
A `<canvas>`, `<video>` (without `<track>`), or similar non-text element exists in a factual content area, and no equivalent textual representation of the element's content can be found in the page HTML.

## Automated Decision Boundary
A finding is generated when:
1. A non-text content element (`<canvas>`, `<video>`, `<object>`, `<embed>`, or non-extractable SVG) is identified in a factual content area, AND
2. For `<video>`: no `<track>` element exists AND no transcript text is nearby, AND
3. For `<canvas>`: no fallback content, `aria-label`, or `aria-describedby` exists, AND
4. No equivalent factual text is found in the surrounding HTML (within the same section/article), AND
5. The element's context suggests it communicates important factual information (based on heading association, page type, size/prominence)

## Potential Severity

**High**: Critical factual information (pricing, specifications, instructions) is locked in non-text elements with no text alternative.

**Medium**: Important but non-critical information is non-text-only.

**Low**: Supplementary visual content lacks text alternatives.

Severity depends on: importance of locked content, number of affected elements, whether the non-text content is the primary information delivery mechanism for important facts.

## Potential Remediation
Provide equivalent readable text for important information communicated through non-text elements. For videos: add `<track>` elements with captions or provide a transcript. For canvas: include fallback content within the `<canvas>` tags and ARIA attributes. For data visualizations: provide a data table equivalent. For SVGs: use `<text>` elements or provide descriptive text. For CSS-generated content: move factual text into the HTML DOM.

## Current Evidence

**SOURCE-DERIVED FACT**: W3C WCAG 2.2 Success Criterion 1.2.1 (Audio-only and Video-only) and 1.2.2 (Captions) require text alternatives for time-based media. This standard directly addresses the machine-readability of video content.

**SOURCE-DERIVED FACT**: The HTML specification defines `<canvas>` fallback content: "Authors should provide alternative content inside the canvas element" for when the canvas is not available or cannot be interpreted.

**SOURCE-DERIVED FACT**: The Round 3 Handbook Section F describes content "carried by something a summarizer can't read" — `<canvas>`, `<video>` without transcript, and CSS-generated text are examples of this.

**OUR INFERENCE**: Non-text presentation layers that communicate important facts without text equivalents create information lock-in for text-oriented machine readers.

**UNPROVEN DOWNSTREAM EFFECT**: Some AI systems have multimodal capabilities (video understanding, image analysis) that could partially address this. The claim is limited to text-oriented readers.

## Counterexamples

1. **Video with full captions/transcript** → NOT a finding. The `<track>` element or page transcript provides the text equivalent.

2. **Canvas used for decorative animation** → NOT a finding. Loading spinners, background effects, and decorative animations don't contain factual content.

3. **SVG with extractable `<text>` elements** → NOT a finding. If the SVG's text content is encoded as `<text>` elements, standard text extraction can access it.

4. **Interactive chart with accessible data table** → NOT a finding. If the page provides a `<table>` containing the same data visualized in the chart, the facts are accessible.

5. **Video introduction/testimonial** → NOT a finding (usually). Video testimonials typically don't contain unique factual claims not available elsewhere on the page.

## Known Limitations
- Cannot determine whether a canvas/video actually contains factual content without viewing it (uses context heuristics)
- Canvas and video content analysis would require expensive computer vision / multimodal processing (intentionally avoided)
- This failure mode may be less common than image-only lock-in (F-001)
- Some AI systems have multimodal capabilities that reduce the practical impact
- CSS-generated content detection requires parsing stylesheets, adding complexity

## Experiment Design

1. **Condition tested**: Important facts in canvas/video/non-text with no text equivalent
2. **Expected bad outcome**: Text-oriented reader cannot extract those facts
3. **Ground truth**: Manual identification of factual content in non-text elements
4. **Supports hypothesis**: Non-text element contains key facts, no track/transcript/fallback
5. **Kills hypothesis**: All non-text elements are decorative or have text equivalents
6. **Obvious false positives**: Decorative canvas, videos with captions, SVGs with text elements
7. **Automatable**: Partially — element detection yes; content importance requires heuristics
8. **Works on unseen site**: Yes — HTML element analysis is generic
9. **Evidence emitted**: List of non-text elements with caption/transcript/fallback analysis
