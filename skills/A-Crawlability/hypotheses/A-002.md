# A-002 — Non-Crawlable Navigation

## Mechanism
crawl

## Concrete Claim

IF:
important public pages are reachable by a human through in-page interactions (JavaScript click handlers, infinite scroll, "Load More" buttons, client-side routing without standard links) but are NOT represented by standard crawlable `<a href="...">` links in the initial HTML or in a sitemap,

THEN:
a crawler that follows the site's discoverable link graph from the initial HTML will fail to discover those pages, because their URLs are not exposed through any crawlable mechanism.

## Evidence Needed

### To Confirm
- Parse the initial HTML to extract all standard `<a href>` links (the static link graph)
- Fetch and parse sitemap.xml (if present) to identify additional declared URLs
- Render the page with JavaScript and extract all URLs exposed after rendering (the rendered link graph)
- Identify URLs that appear ONLY in the rendered link graph (not in static links or sitemap)
- Verify that those render-only URLs serve important content (not tracking pixels, analytics, or UI fragments)
- Confirm that no alternate crawl path (sitemap, RSS, alternate navigation page) exposes those URLs

### To Reject or Narrow
- The render-only URLs are also present in the sitemap → the sitemap provides an alternate crawl path
- The render-only URLs are duplicates of URLs already in the static link graph (different format, same destination)
- The render-only URLs lead to supplementary or non-essential content
- The JavaScript generates proper `<a href>` tags that a post-render crawler could follow (Google's rendering pipeline would discover them)
- The URLs are fragment-based (`#section`) and do not represent distinct pages

## Observable Signal
Important destination URLs appear in the rendered DOM but are absent from both the initial HTML `<a href>` links and the sitemap.

## Automated Decision Boundary
A finding is generated when:
1. A URL appears in the rendered DOM (as a navigable link or destination) that was NOT present as a standard `<a href>` in the initial HTML, AND
2. The URL is NOT listed in sitemap.xml (if available), AND
3. The URL serves genuinely distinct, important content (not a fragment, tracking URL, or duplicate), AND
4. The URL is on the same domain or a known subdomain, AND
5. At least 3 such URLs are identified (threshold to avoid flagging isolated interactive elements)

## Potential Severity

**High**: An entire content category is discoverable only through JavaScript interaction (e.g., all product pages behind a JS-only "Load More" in a catalog).

**Medium**: A meaningful subset of important pages (5-20%) are only JS-discoverable.

**Low**: A small number of supplementary pages are JS-only discoverable.

Severity depends on: number of affected pages, importance of content, whether a sitemap exists as fallback.

## Potential Remediation
Ensure that every important destination page is represented by at least one standard crawlable `<a href="URL">` link in the site's navigable HTML, or is included in the sitemap.xml. For paginated content, use `<a href>` links for pagination controls rather than JavaScript-only "Load More" handlers. For infinite scroll implementations, provide a paginated HTML fallback with crawlable links.

## Current Evidence

**SOURCE-DERIVED FACT**: Google Search Central documentation explicitly states that Google primarily discovers pages through links: "Google discovers URLs by following links." Standard `<a>` elements with `href` attributes are the primary discovery mechanism.

**SOURCE-DERIVED FACT**: Google documents that URLs generated by JavaScript `onclick` handlers or non-standard elements without `href` attributes may not be reliably discovered: "To be discovered, links should be `<a>` HTML elements with an `href` attribute."

**SOURCE-DERIVED FACT**: Google's rendering pipeline does execute JavaScript and can discover JS-generated links, but this is a secondary, resource-intensive process that may be delayed or incomplete. Non-Google crawlers (including many AI assistant retrieval systems) may not render JavaScript at all.

**OUR INFERENCE**: Pages that are only discoverable through JavaScript interaction and are not in the sitemap face a higher risk of not being discovered by crawlers that do not render JavaScript.

**UNPROVEN DOWNSTREAM EFFECT**: Direct impact on AI assistant citations is not established. The claim is limited to the crawl discovery gate.

## Counterexamples

1. **JS button exists but URLs are also in normal links** → NOT a finding. If the same destination URLs appear as standard `<a href>` links elsewhere on the page or site, the JS-only interaction is merely an additional UX path.

2. **JS-only links but all URLs are in sitemap** → NOT a finding (reduced severity). The sitemap provides an alternate discovery path; the finding should be downgraded or suppressed.

3. **Fragment-only navigation (`#section`)** → NOT a finding. Fragment-based navigation within a single page does not represent undiscoverable pages.

4. **Single-page application with proper `<a href>` links** → NOT a finding. Modern SPAs (using frameworks like Next.js, Nuxt) often generate proper crawlable links despite using client-side routing.

5. **Interactive filtering that doesn't create new pages** → NOT a finding. If a JavaScript filter modifies the current page's content without creating distinct addressable pages, there are no undiscoverable pages.

## Known Limitations
- Determining "important" content requires heuristics (page type, heading structure, content length)
- Full link graph comparison requires rendering, which adds time and complexity
- Cannot detect all JS-generated URLs without full interaction simulation (clicking every button)
- Bounded to sampled pages; cannot exhaustively audit entire site
- Google's rendering pipeline may eventually discover JS-only links, reducing the severity for Google-indexed content specifically (but not for other crawlers)

## Experiment Design

1. **Condition tested**: Important URLs discoverable only through JS interaction
2. **Expected bad outcome**: Static crawler misses those pages entirely
3. **Ground truth**: Compare static link graph + sitemap vs rendered link graph
4. **Supports hypothesis**: Important URLs in rendered-only set with no sitemap/link fallback
5. **Kills hypothesis**: All important URLs are in static links or sitemap
6. **Obvious false positives**: Fragment navigation, sitemap-covered URLs, filter interactions
7. **Automatable**: Yes — with headless browser
8. **Works on unseen site**: Yes — link parsing is generic
9. **Evidence emitted**: List of render-only URLs with importance classification
